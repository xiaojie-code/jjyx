---

## 1. 代码修改规范

```markdown
# 代码修改规范

- 改完代码必须编译验证，不能留编译错误
- 修改文件后检查诊断信息，确认零错误再继续
- 不要引入新的依赖库，除非明确要求
- 保持现有代码风格，不要擅自重构不相关的代码
- 一次只改一个功能点，不要顺手改别的
- 如果改动超过 3 个文件，先说明方案再动手
- 删除代码前确认没有其他地方引用
```

## 2. Bug 排查规范

```markdown
# Bug 排查规范

- 先看日志和错误信息，不要猜
- 定位问题后先确认根因，不要头痛医头
- 同一个方案失败两次，换思路，不要死磕
- 修复后必须验证，能跑通再说修好了
- 如果问题涉及多个模块，先画出调用链路
- 不确定的地方加日志输出，不要凭感觉判断
- 修复一个 bug 时不要引入新的 bug
```

---

## 3. 文件操作规范

```markdown
# 文件操作规范

- 大文件（超过 150 行）分段写入，先 fs_write 前 50 行，再 fs_append 分批追加
- 不要用 PowerShell 的 Set-Content 处理包含中文的文件（会破坏编码）
- 处理中文文件用 Node.js 的 fs 模块，指定 utf8 编码
- 创建多个文件时逐个创建，不要并行
- 修改文件前先读取确认内容，不要盲改
- 临时文件用完即删
```

---

## 4. Git 操作规范

```markdown
# Git 操作规范

- 提交前确认所有修改都能编译通过
- commit message 用中文，简洁说明改了什么
- 不要把 node_modules、dist、.env 提交进去
- 推送到新分支，不要直接推 main
- 大改动拆成多个小 commit，方便回滚
- 不确定的改动先 stash，确认后再提交
```

## 5. API 设计规范

```markdown
# API 设计规范

- RESTful 风格：GET 查询、POST 创建、PUT 更新、DELETE 删除
- 路径用复数名词：/api/users、/api/messages
- 分页参数统一：page + pageSize
- 返回格式统一：{ data, message, code } 或直接返回数据
- 错误返回 HTTP 状态码 + 中文错误消息
- 敏感操作需要鉴权，用 Guard 或中间件统一处理
- 接口幂等性：同一请求多次调用结果一致
```

## 6. 数据库操作规范

```markdown
# 数据库操作规范

- 不要在循环中执行单条查询（N+1 问题），用批量查询或 JOIN
- ID 字段比较时注意类型转换（数据库可能返回 string）
- 涉及多表修改用事务包裹
- 删除操作用软删除（status 字段），不要物理删除
- 大批量操作分批执行，避免锁表
- 索引加在经常查询的字段上，不要滥加
```

## 7. 前端开发规范

```markdown
# 前端开发规范

- 组件拆分：超过 200 行的组件考虑拆分
- 状态管理：全局状态用状态管理库，局部状态用组件内 state
- 异步操作：加 loading 状态，加错误处理，加 mounted 检查
- 列表渲染：加 key，大列表用虚拟滚动
- 表单提交：防重复点击，提交后禁用按钮
- 实时数据：先本地更新 UI，再异步同步服务器
- 路由跳转：返回时刷新数据，确保状态一致
```

## 8. WebSocket / 实时通信规范

```markdown
# WebSocket 实时通信规范

- 连接前先注册事件监听器，再建立连接
- 断线自动重连，重连后重新拉取离线数据
- 消息推送包含完整信息（ID、内容、发送者昵称等），减少二次查询
- 在线状态用 Map 管理，key 统一为 Number 类型
- 离线消息持久化存储，上线后主动推送
- 心跳检测：定期 ping/pong，超时断开
- 消息去重：用消息 ID 判断是否已处理
```

## 9. 安全规范

```markdown
# 安全规范

- 密码不明文存储，用 bcrypt 哈希
- JWT token 设置过期时间，敏感操作二次验证
- 用户输入必须校验和转义，防 XSS 和 SQL 注入
- 文件上传限制类型和大小
- 接口限流，防止暴力请求
- 敏感信息（密钥、数据库密码）放环境变量，不要硬编码
- 日志中不要打印用户密码和 token
```

## 10. 性能优化规范

```markdown
# 性能优化规范

- 数据库查询加索引，避免全表扫描
- 频繁读取的数据加缓存（Redis）
- 大列表分页加载，不要一次返回全部
- 图片压缩后再上传，用 CDN 分发
- 前端资源懒加载，首屏只加载必要内容
- 接口响应超过 500ms 需要优化
- 避免在循环中做 IO 操作（网络请求、文件读写）
```

## 11. 项目管理规范

```markdown
# 项目管理规范

- 每次开发前先看需求文档，确认理解一致
- 大功能拆成小任务，每个任务可独立验证
- 改动影响范围大时，先写方案文档再动手
- 遇到阻塞问题及时沟通，不要闷头死磕
- 完成后自测，至少覆盖正常流程和主要异常
- 代码合并前 review，至少过一遍 diff
- 上线后观察日志，确认无异常
```

## 12. 文档规范

```markdown
# 文档规范

- README 包含：项目简介、技术栈、启动方式、目录结构
- API 文档随代码同步更新
- 复杂业务逻辑写注释说明"为什么"，不只是"做了什么"
- 配置项加注释说明用途和可选值
- 变更日志记录每次发版的改动
- 文档用中文，代码注释用中文
```

## 使用方式

1. 选择需要的规范，复制对应的 markdown 代码块内容
2. 放到项目的 `.kiro/steering/` 或 `.cursor/rules/` 目录下
3. 文件名建议：`coding-standards.md`、`bug-fix-guide.md`、`api-design.md` 等
4. 可以根据项目实际情况增删条目
