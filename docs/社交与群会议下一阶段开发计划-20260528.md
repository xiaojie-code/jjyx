# 社交与群会议下一阶段开发计划

生成日期：2026-05-28

## 一、当前基线

当前项目已经完成一版社交和群会议基础能力：

- 一对一聊天、群聊基础链路已接入 Socket.IO 实时推送。
- 图片消息、消息编辑、禁言、踢人、设置管理员、解散群等群聊能力已补齐基础版。
- 后端已有会议记录、会议参与者、会议禁入表，以及会议开始、加入、离开、结束、踢人等接口。
- 管理后台已有社交管理入口，可查看聊天记录、会议列表、强制结束会议、维护回放地址、清理过期数据。
- App 已支持 API/WS 地址通过 `--dart-define` 注入，后续打包到手机端时不能再依赖 `localhost`。
- 会议页已经接入 `flutter_webrtc` P2P MVP，本地摄像头/麦克风、会议 Socket 信令、offer/answer/candidate 转发、麦摄状态同步和基础宫格已经具备。

当前会议能力已经从“业务记录 + 成员管理 + 信令基础”推进到“P2P WebRTC 真机联调”阶段。接下来最重要的不是立刻做 SFU 和录制，而是先把手机端多人会议里的声音、画面、重连、权限和调试可视化跑稳。

## 二、总体方向

下一阶段的重点不是一次性做完整的“腾讯会议”，而是先把手机端能稳定跑的音视频会议 MVP 做出来，然后再扩展多人 SFU、录制和回放。

推荐推进原则：

1. 先 Android/iOS 真机可用，再考虑 Flutter Web 展示效果。
2. 先 P2P 或小规模 WebRTC 会议跑通，再接 mediasoup / Janus。
3. 先保证会议进入、离开、断线、被踢、权限、积分扣除稳定，再做录制和回放。
4. 所有新功能都要考虑手机端打包后的网络地址、权限声明、Socket 连接、资源加载。

## 三、第一阶段：真机音视频会议 MVP

目标：让群会议从“会议房间页面”升级为“真机可以打开摄像头和麦克风，并能完成基础音视频通话”。

### 3.1 App 端

- 接入 `flutter_webrtc`。
- 会议页显示本地摄像头预览。
- 支持打开/关闭麦克风。
- 支持打开/关闭摄像头。
- 支持前后摄像头切换。
- 支持加入会议、离开会议、被踢后退出会议页。
- 增加会议连接状态：连接中、已连接、重连中、已断开。
- Android 增加摄像头、麦克风、网络权限。
- iOS 后续打包时增加摄像头、麦克风权限说明。

### 3.2 后端信令

- 完善 `MeetingGateway` 信令事件。
- 支持 `meeting:join`、`meeting:leave`、`meeting:signal`。
- 增加 offer、answer、ice candidate 转发。
- 增加麦克风/摄像头状态同步事件。
- 被踢用户要立即收到通知，并且不能再次加入当前会议。
- 后台强制结束会议时，会议内所有用户要收到结束通知。

### 3.3 验证重点

- 两台真机在同一局域网内能互相看到/听到。
- 真机使用 `--dart-define=API_BASE_URL=... --dart-define=WS_BASE_URL=...` 后能正常登录和连接 Socket。
- App 切后台再回来后，会议不会直接卡死。
- 断网重连后，会议状态能恢复或明确提示退出重进。

## 四、第二阶段：群聊体验补强

目标：把聊天体验补到更接近日常社交软件，优先补用户高频操作。

- 图片消息支持“相册选择 + 拍照发送”。
- 语音消息支持长按录音、松开发送、上滑取消。
- 聊天记录支持上拉分页加载，避免一次加载过多消息。
- 会话列表里的最后一条消息显示 `[图片]`、`[语音]` 等预览文案。
- 消息搜索结果支持跳转到对应聊天位置。
- 群成员添加从“输入用户 ID”升级为“从联系人列表选择”。
- 联系人搜索支持账号、昵称、备注。
- 群成员列表支持搜索成员。
- 后续可增加群公告、我在本群昵称、群头像等增强项。

## 五、第三阶段：管理后台完善

目标：让后台可以真正支撑运营和排查问题。

- 社交管理页增加分页。
- 聊天记录支持按时间范围、消息类型、群聊/单聊筛选。
- 聊天记录支持查看上下文。
- 会议列表支持查看参会成员明细。
- 会议列表支持查看被踢成员。
- 强制结束会议后，前端会议页要实时收到结束通知。
- 清理过期数据后展示结果：清理消息数、会议数、文件数。
- 系统配置里重点维护：
  - `data_retention_days`：聊天和会议数据保留天数。
  - `meeting_start_cost`：普通成员发起会议消耗积分。

## 六、第四阶段：多人会议 SFU 和录制

目标：从小规模 WebRTC 会议升级到真正多人会议架构。

这部分建议等第一阶段真机 MVP 稳定后再做，因为它涉及额外服务部署、带宽、NAT 穿透和录制存储。

### 6.1 媒体服务器

- 选择 mediasoup 或 Janus。
- 部署独立媒体服务器。
- 配置公网 IP、UDP 端口、防火墙。
- 准备 TURN 服务，比如 coturn，用于复杂网络环境穿透。

### 6.2 后端对接

- NestJS 对接媒体服务器房间。
- 创建 router、transport、producer、consumer。
- 管理会议成员和媒体流关系。
- 会议结束时释放媒体资源。

### 6.3 App 端升级

- 从 P2P 信令切换到 SFU 模式。
- 支持多人视频布局。
- 支持成员摄像头状态、麦克风状态展示。
- 支持弱网提示和重连。

### 6.4 录制和回放

- 服务端录制会议。
- 录制文件保存到 OSS 或本地磁盘。
- 录制完成后自动写入 `recording_url`。
- 管理后台支持播放回放。
- 清理任务同时清理过期录制文件。

## 七、第五阶段：测试和打包

目标：确保功能不是只在 Web 或本机能跑，而是手机包也能正常使用。

### 7.1 真机测试

- Android 真机登录、聊天、图片发送、会议加入、会议离开。
- Android 真机摄像头、麦克风权限弹窗和拒绝权限后的提示。
- Android 真机断网、切后台、锁屏、恢复前台。
- 后续如需 iOS，也要单独测试权限和 WebRTC 表现。

### 7.2 后端测试

- 多用户同时在线。
- 群消息广播。
- 离线消息推送。
- 禁言后文字、图片、语音都不能发送。
- 普通成员发起会议扣积分。
- 余额不足时不能发起会议。
- 群主/管理员发起会议免费。
- 被踢用户不能再次加入同一场会议。
- 后台强制结束会议后，App 端同步退出或提示。

### 7.3 打包参数

手机端打包时要指定真实可访问的后端地址：

```bash
--dart-define=API_BASE_URL=http://你的服务器地址:3001
--dart-define=WS_BASE_URL=http://你的服务器地址:3001
```

局域网真机调试时，不能使用 `localhost`，要使用电脑局域网 IP 或测试服务器地址。

## 八、建议执行顺序

建议按下面顺序推进：

1. 真机联调前先确认当前电脑 WLAN IPv4，再用这个地址重启后端、Flutter Web，并重新打 Android 包。
2. 先把当前 P2P 会议跑稳：电脑 Web + 两台 Android 真机进入同一会议，确认互相能看到画面、听到声音。
3. 给会议页加诊断面板，显示每个 peer 的 socket、connectionState、iceConnectionState、signalingState、offer/answer/candidate 次数，以及 audio/video track 收发状态。
4. 完善会议异常处理：断线重连、切后台恢复、摄像头切换后的重新协商、被踢、强制结束、离开会议后的资源释放。
5. 落地普通成员发起会议扣积分：配置 `meeting_start_cost`，群主/管理员免费，普通成员余额足够才扣积分发起。
6. 补群聊高频体验：语音长按录音、聊天记录分页、联系人多选拉群、成员搜索、消息搜索跳转。
7. 补管理后台分页、筛选、会议成员明细、被踢成员、清理结果统计和系统配置入口。
8. P2P 真机 MVP 稳定后，再接 TURN、mediasoup / Janus、录制、回放和 OSS 存储。

## 九、近期最小可交付版本

近期建议先交付一个“小而稳”的版本：

- 两台 Android 真机能进入同一个群会议。
- 双方能看到/听到对方。
- 能关闭/打开麦克风和摄像头。
- 群主或管理员能结束会议、踢出成员。
- 被踢成员不能重新加入本场会议。
- 普通成员发起会议会扣积分。
- 后台能看到进行中的会议并强制结束。

这个版本完成后，群会议功能才算真正从“业务骨架”进入“可用会议”的阶段。

## 十一、SFU、录制、回放方案整理（2026-05-29 更新）

### 11.1 当前结论

- 当前会议仍然是 P2P WebRTC 模式，NestJS 后端只负责业务接口和信令转发，不直接接收音视频媒体流。
- 当前回放能力是“播放已有回放地址”：会议记录里有 `recording_url` 时，管理后台可以打开播放器查看。
- 真正的“会议结束后自动生成视频回放”需要接入 SFU 媒体服务器，让服务端能拿到媒体流并录制。
- 后续推荐优先使用 mediasoup，配合 coturn 和本地磁盘/OSS 存储；Janus 可作为备选方案。
- 目前已经完成一部分前置能力：后端媒体配置接口、App 动态 ICE/TURN 配置、SFU endpoint 配置预留、后台回放播放、清理文件数量统计。

### 11.2 推荐部署架构

```text
Flutter App
  ├─ REST / Socket.IO ─────────────── NestJS 后端
  │                                      ├─ 会议业务、鉴权、成员管理
  │                                      ├─ SFU 房间和流关系管理
  │                                      └─ recording_url 写入和清理
  └─ WebRTC 媒体流 ────────────────── mediasoup SFU
                                         ├─ producer / consumer
                                         ├─ transport 管理
                                         └─ 录制流输出

复杂网络穿透：coturn
录制文件存储：本地 uploads/recordings 或 OSS
管理后台：播放 recording_url，查看会议和成员明细
```

测试环境可以先把 NestJS、mediasoup、coturn、MySQL、Redis 放在同一台公网服务器上。正式环境建议把媒体服务器单独拆出来，选择带宽和 UDP 转发能力更好的机器。

### 11.3 服务器准备

- 准备一台公网服务器，最好有固定公网 IP。
- 开放业务端口：例如后端 `3001`、后台 `3100` 或前端站点端口。
- 开放 coturn 端口：常用 `3478/udp`、`3478/tcp`，如需 TLS 可加 `5349`。
- 开放 mediasoup UDP 端口段：例如 `40000-49999/udp`，具体端口段后续写入配置。
- 部署 coturn，用于跨网络、弱 NAT、运营商网络下的媒体中继。
- 部署 mediasoup 服务，可以先作为 NestJS 同仓库里的独立模块或独立 Node 进程运行。
- 准备录制文件目录或 OSS bucket，并确定访问 URL 的拼接规则。

### 11.4 后端改造方向

- 保留当前 `/api/social/meetings/:id/media-config`，继续作为 App 获取媒体模式、TURN、SFU、录制状态的入口。
- 增加更多系统配置：SFU 公网 IP、listen IP、announced IP、UDP 端口段、录制存储方式、录制目录、OSS 配置。
- 会议开始时创建 SFU room/router，会议结束时释放 router、transport、producer、consumer。
- 增加 SFU 信令事件或接口：创建 transport、连接 transport、发布 producer、订阅 consumer、关闭 producer、成员离开清理资源。
- 将会议成员和媒体流绑定起来，后台能看到谁开了摄像头、谁开了麦克风、谁正在推流。
- 录制完成后自动写入 `recording_url`，并记录录制状态、时长、文件大小，方便后台展示和清理。

### 11.5 App 改造方向

- 进入会议时先读取 media-config，根据 `mediaMode=p2p/sfu` 走不同会议链路。
- P2P 模式继续保留，作为局域网和小规模会议的兜底方案。
- SFU 模式下，App 本地音视频变成 producer，远端成员音视频变成 consumer。
- Flutter 侧仍然使用 `flutter_webrtc` 承载摄像头、麦克风和渲染；如果选择 mediasoup，需要接入 mediasoup 的 Flutter/Dart 客户端能力，或封装一层 SFU transport 适配。
- 会议页继续复用现有宫格、麦克风/摄像头状态、成员状态展示，同时补弱网提示和重连状态。

### 11.6 录制和回放方向

- 不建议在手机端录制完整会议，应该由服务端从 SFU 侧录制。
- 录制方案可以先做最小版：单会议自动录制混流或分轨，输出 `.webm` 或 `.mp4` 文件。
- mediasoup 常见做法是通过 PlainTransport 把音视频流送到 FFmpeg/GStreamer，再由录制进程写文件。
- 录制完成后，后端把文件地址写入会议记录的 `recording_url`。
- 管理后台现有播放器继续复用，后续只需要展示录制状态、文件大小、时长和下载/删除按钮。
- 清理任务继续复用现有过期数据清理能力，把录制文件纳入删除统计。

## 十二、接下来应该做什么

### 12.1 现在马上做

当前最应该先把 P2P 真机会议跑稳。SFU 会把网络、媒体流、录制、服务部署复杂度都放大，如果 P2P 阶段的问题还没定位清楚，直接上 SFU 会更难排查。

建议下一步按这个顺序做：

1. 增加会议诊断面板：显示 Socket 状态、join ack、每个 peer 的连接状态、ICE 状态、信令状态、offer/answer/candidate 数量、audio/video track 收发状态。
2. 用电脑 Web + 两台 Android 真机做三端复测，记录每个端是否能看到远端画面、是否能听到远端声音。
3. 优先修复音视频稳定性：远端画面缺失、开麦无声、切换摄像头后重新协商、切后台恢复、断网重连提示。
4. 验证 TURN 配置链路：先用当前 media-config 下发 TURN，再确认 App 建连时确实使用了 TURN server。
5. 把系统配置入口补完整：让后台可以维护 TURN、SFU endpoint、媒体模式、录制开关，而不是只靠数据库默认值。

### 12.2 P2P 稳定后做 SFU 最小 PoC

P2P 真机会议稳定后，再开始 SFU 最小闭环，不要一上来就做完整录制和大规模会议。

最小 PoC 目标：一个会议房间，一个用户发布音视频，其他用户通过 SFU 订阅并看到/听到。

建议顺序：

1. 新增 mediasoup 服务模块或独立进程，先跑通 worker、router 创建。
2. 后端加 SFU transport、producer、consumer 的最小信令接口。
3. App 在 `mediaMode=sfu` 时走 SFU 分支，先实现发布本地音视频。
4. 再实现订阅远端 producer，并复用当前会议宫格显示。
5. 用配置开关保留 P2P/SFU 双模式，方便出问题时回退。
6. SFU 音视频稳定后，再接录制进程和 `recording_url` 自动写入。

### 12.3 暂时不要急着做

- 暂时不要在 P2P 模式上硬做服务端自动录制，因为后端拿不到完整媒体流。
- 暂时不要直接把所有会议切到 SFU，先做单房间 PoC 和灰度开关。
- 暂时不要先做复杂 OSS、转码、封面图、下载权限，等录制主链路打通后再补。
- 暂时不要把录制回放当成当前问题的排查工具，当前更需要诊断面板和真机三端日志。
